Hermes Worker kurulum, kurtarma ve tanılama rehberi

Yeni Windows laptopta WSL2 + Docker + .NET 8 kurulumu, taşınabilir kitin geri yüklenmesi, Worker–Server eşleştirmesi, CLIProxy doğrulaması, systemd yönetimi, Desktop başlangıç tanısı ve güvenli Server yayını için tek kaynak.

2 çalışma moduDocker image veya native .NET
4 sağlık katmanıBağlantı, Hermes, model, storage
0 gerçek secretRehber yalnız placeholder içerir
E2E hedefiQueued → Claimed → Running → Completed

1. Güvenlik ve değişiklik sınırları

Komutları çalıştırmadan önce etiketi ve doğru kabuğu kontrol et.

Salt-okunur

Güvenli inceleme

Durum, sürüm, dosya yolu, checksum, servis çıktısı ve sınırlı log okunabilir. Sistem durumu değiştirilmez.

Runtime değiştirir

Çalışma durumunu etkiler

Docker image yüklemek, paket kurmak veya user service başlatmak runtime durumunu değiştirir.

Onay gerekir

Yayın ve rollback

Symlink değiştirme, servis restart, veritabanı yedeği/geri yükleme, aktif release geçişi onay gerektirir.

Özel dosya gerekir

Rehberde bulunmaz

Worker tokenı, Worker ID, Server URL, seed, CLIProxy anahtarı ve gerçek endpoint private kanaldan sağlanır.

Asla pakete veya public repoya koyma: gerçek .env/worker.env, token, API key, sertifika, SQLite, log, kullanıcı verisi, workspace, Docker volume/container/credential/cache durumu, bin, obj ve IDE geçici dosyaları.

Mevcut kit yeni laptopta Worker kurulumu için yeterlidir; eşleştirme ve CLIProxy bilgileri güvenlik nedeniyle bilinçli olarak dışarıdadır.

3. Yeni laptopta sıfırdan kurulum

Sıra önemlidir. Bir katman doğrulanmadan sonraki katmana geçme.

Yönetici PowerShell

WSL2 ve Ubuntu

wsl --install -d Ubuntu
wsl --update
wsl --status

Windows yeniden başlatma isterse tamamla. Ubuntu ilk açılışında Linux kullanıcı adı ve parolası oluştur.

WSL / Ubuntu

systemd etkinleştir

sudo nano /etc/wsl.conf
[boot]
systemd=true

Kaydettikten sonra Windows PowerShell'de:

wsl --shutdown

Ubuntu yeniden açıldığında:

systemctl --version
systemctl --user is-system-running || true
Windows + WSL

Docker Desktop ve WSL entegrasyonu

Docker Desktop → Settings → Resources → WSL Integration → Ubuntu: Enabled.

docker version
docker run --rm hello-world
Bu iki komut çalışmadan Worker kurulumuna geçme.
WSL / Ubuntu

.NET 8 araçlarını kur

sudo apt update
sudo apt install -y dotnet-sdk-8.0 git zip curl ca-certificates
dotnet --info
WSL / Ubuntu

Hermes image doğrula ve yükle

cd /mnt/c/Users/MONSTER/Desktop/SORUNCOZUMVEYEDEKWORKER/VORTEX_PORTABLE_BACKUP_20260731T121253Z
sha256sum -c image/vortex-hermes-0.18.2.tar.sha256
docker load -i image/vortex-hermes-0.18.2.tar
docker image inspect vortex-hermes:0.18.2
docker run --rm vortex-hermes:0.18.2 --help
Smoke test ≠ E2E: Bu sonuç yalnız Docker ve image katmanının çalıştığını gösterir; Server bağlantısını kanıtlamaz.
WSL / Ubuntu

Worker release dizinini hazırla

mkdir -p "$HOME/vortex-worker/releases"
mkdir -p "$HOME/vortex-worker/secrets"
mkdir -p "$HOME/vortex-worker/data"
chmod 700 "$HOME/vortex-worker/secrets"

tar -xzf \
  /mnt/c/Users/MONSTER/Desktop/SORUNCOZUMVEYEDEKWORKER/VORTEX_PORTABLE_BACKUP_20260731T121253Z/release/worker-release-20260722T142640Z.tar.gz \
  -C "$HOME/vortex-worker/releases"

ls -lah "$HOME/vortex-worker/releases"

Gerçek çıkarılan klasör adını gördükten sonra symlink oluştur:

ln -sfn \
  "$HOME/vortex-worker/releases/worker-release-20260722T142640Z" \
  "$HOME/vortex-worker/current"

readlink -f "$HOME/vortex-worker/current"

4. Kit dışında hazırlanacak private dosyalar

Bu değerlerin kitte bulunmaması bir eksik değil, güvenlik gereğidir.

Gerekli özel değerler

  • VORTEX_WORKER_TOKEN
  • VORTEX_WORKER_ID
  • Gerçek VORTEX_SERVER_URL
  • hermes-config.yaml
  • hermes.env
  • CLIProxy endpointi / portu
  • CLIProxy veya provider API key

Hedef WSL düzeni

~/vortex-worker/ ├─ releases/ ├─ current/ ├─ data/ └─ secrets/ ├─ worker.env ├─ hermes-config.yaml └─ hermes.env
worker.env yolu: ~/vortex-worker/secrets/worker.env — izin: chmod 600 "$HOME/vortex-worker/secrets/worker.env". Şablon olarak templates/deploy/wsl/vortex-hermes-worker.env.example kullanılır.

6. CLIProxy / model router

Port ve rota tahmin edilmez; canlı private kurulumdan doğrulanır.

Eski örneklerde 8317/v1 ve 20128/api/v1 gibi çelişen değerler bulunduğu için kopyala-yapıştır kullanılmamalıdır.

OPENAI_BASE_URL=http://host.docker.internal:<DOGRU_PORT>/v1
  • CLIProxy Windows host'ta mı, WSL içinde mi çalışıyor?
  • Docker container içinden host.docker.internal erişilebilir mi?
  • OpenAI-compatible doğru rota gerçekten /v1 mi?
  • Auth gerekiyorsa anahtar private environment içinde mi?

7. systemd user service

Servis şablonunu gerçek release ve private dosya yollarına göre uyarladıktan sonra etkinleştir.

WSL / Ubuntu

Şablon: templates/vortex-hermes-worker.service.example
Hedef: ~/.config/systemd/user/vortex-hermes-worker.service

systemctl --user daemon-reload
systemctl --user enable --now vortex-hermes-worker
systemctl --user status vortex-hermes-worker --no-pager -l
loginctl enable-linger "$USER"
WSL ve Docker'ın Windows açılışında her koşulda otomatik hazır olacağı garanti edilmez. Katmanları ayrı ayrı kontrol et.

8. Katmanlı doğrulama

Health endpointi tek başına yeterli değildir; kontrollü bir iş tamamlanmalıdır.

WSL→systemd→Docker / image→Private dosyalar→Heartbeat→/health/worker→E2E job
WSL / Ubuntu
docker version
docker image inspect vortex-hermes:0.18.2
systemctl --user status vortex-hermes-worker --no-pager -l
journalctl --user -u vortex-hermes-worker -n 100 --no-pager

Server tarafında beklenen health alanları:

workerConnected: true
hermesReady: true
modelReady: true
storageHealthy: true
Gerçek başarı ölçütü: hassas olmayan kontrollü mesajın Queued → Claimed → Running → Completed akışını tamamlaması.

10. Windows Desktop .dll başlangıç tanısı

MainWindow görünmeden kapanan süreç, Worker sorunundan ayrı bir yerel başlangıç hatasıdır.

Salt-okunur kontroller

  • Çalıştırılan DLL'nin kesin yolu
  • dotnet --info ve gerekli runtime
  • .runtimeconfig.json / .deps.json varlığı
  • Çalışma dizini ve publish çıktısı
  • %LOCALAPPDATA%\VortexAI\logs\desktop-startup.log

Hata sınıfları

  • Eksik runtime veya DLL
  • Yanlış çalışma dizini
  • Config/settings yükleme
  • XAML/UI başlangıcı
  • Backend yapılandırması
  • Başarılı açılıştan sonra Worker/E2E hattı
Tanı kanıtları sunulmadan app data silme, ayar sıfırlama, kaldırıp yeniden kurma veya servis restart yapma.

11. Canlı Vortex.Server yayını

/api/diagnostics/worker 404 dönüyorsa güncel kod ile canlı release/proxy arasında fark olabilir.

Salt-okunur
  • systemd unit: ExecStart, User, WorkingDirectory, EnvironmentFile
  • Aktif release/current symlink hedefi
  • Nginx /api ve /health upstream
  • Loopback 127.0.0.1:5000 sağlık yanıtı
  • Data directory / SQLite yolu, .NET 8, disk alanı
  • Public /health, /health/worker, diagnostics başlangıç durumu
Onay gerekir
  1. Private PowerShell scripti ile Release artifact üret.
  2. Manifest ve SHA-256 oluştur; secret dahil etme.
  3. Sunucuda timestamped release dizinine aktar ve doğrula.
  4. Servis durdurulduktan sonra durable data dizinini yedekle.
  5. current symlink'i atomik değiştir.
  6. Yalnız vortex-server servisini yeniden başlat.
Doğrulama
  • Loopback ve public /health başarılı
  • /health/worker başarılı
  • Diagnostics endpoint artık 404 değil
  • Yetkisiz istek 403, yetkili istek 200
  • Kontrollü job için gerçek ErrorCode veya Completed sonucu

12. Rollback ilkeleri

Önce binary/release geri dönüşü; veritabanı geri yükleme yalnız gerektiğinde ve ayrı onayla.

Worker rollback

  1. Önceki release yolunu doğrula.
  2. current symlink'i önceki sürüme çevir.
  3. User service'i yeniden başlat.
  4. Bounded journal ve health kontrolü yap.

Server rollback

  1. Önceki current hedefini geri bağla.
  2. Yalnız vortex-server servisini restart et.
  3. Loopback ve public health'i doğrula.
  4. DB yalnız eski binary yeni migration sonrası DB ile çalışmıyorsa geri yüklenir.

13. Taşınabilir yedek oluşturma standardı

Geniş klasör kopyası yerine açık allowlist kullan.

Dahil edilecekler

  • Vortex.HermesWorker ve Vortex.Shared kaynakları
  • Çözüm/build/NuGet girdileri
  • docker/hermes build context
  • Secret-free service/env şablonları
  • Doğrulanmış release TAR + checksum
  • Tek seçilmiş Hermes image TAR + checksum
  • RESTORE dokümanı ve integrity manifesti

Hariç tutulacaklar

  • Gerçek env, token, key, certificate
  • Data, log, workspace, SQLite
  • Docker volume/container/credential/cache
  • bin, obj, IDE ve temp dosyaları
  • Private Server payload
Secret-safety taraması şüpheli dosya bulursa paket mühürlenmez. Değer değil, yalnız dosya yolu raporlanır.

14. Public export sınırı

Public dağıtım yalnız açık allowlist ve temiz tarama ile genişletilir.

  • Her artifact manifestte tek tek listelenir; wildcard kullanılmaz.
  • Checksum, içeriğin güvenli olduğunu kanıtlamaz; ayrıca içerik taraması gerekir.
  • Private Server/Admin payload, env, seed, DB, log, runtime state dışarıda kalır.
  • CLIProxy yalnız generic OpenAI-compatible topoloji ve <LOCAL_MODEL_ROUTER_URL> placeholder ile anlatılır.
  • Gerçek endpoint, port, token, API key veya ChatGPT oturumu paylaşılmaz.
