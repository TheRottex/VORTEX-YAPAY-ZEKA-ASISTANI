Vortex.Server Operasyon Rehberi

Bu rehber public Vortex.Server içindir. Hermes veya HermesAgent burada kurulmaz, başlatılmaz, Docker içinde çalıştırılmaz.

SınırTopolojiGeliştirmeYapılandırmaKomut KitabıReleaseHealthProxyRollbackYedek

1. Güvenlik sınırı

Kural: Public Server kullanıcı kimliği, API, kota, job queue ve owner-only sonucu yönetir. Gerçek Hermes işlemi yalnız private Vortex.HermesWorker tarafında olur.
  • Public Server üzerinde Hermes, HermesAgent veya Worker Docker container çalıştırma.
  • Worker laptop/WSL tarafından Server'a outbound HTTPS ile bağlanır.
  • Worker için public inbound port açma.
  • Bu rehber Tailscale kurmaz veya başlatmaz.

OAuth ve Kimlik Doğrulama Yapılandırması

  • Google/GitHub OAuth Sağlayıcı İstemci Anahtarları: OAuth__Google__ClientId, OAuth__Google__ClientSecret, OAuth__GitHub__ClientId ve OAuth__GitHub__ClientSecret üretim ortamında güvenli bir şekilde tanımlanmalıdır.
  • Geri Çağırma (Callback) Adresleri: OAuth sağlayıcılarında kayıtlı callback yolları şu formatta olmalıdır: https://vortex.rottexforge.com/api/auth/{provider}/callback
  • Anahtar Varlığı Kontrol Komutları: systemd ortam değişkenleri arasında OAuth anahtarlarının varlığını doğrulamak için şu komut kullanılabilir: 
    systemctl show vortex-server -p Environment --value | tr ' ' '\n' | grep -q '^OAuth__Google__ClientId='
  • Otomasyon Tokenı ve Kimlik Girişi Ayrımı: Otomasyon tokenı (örneğin Worker__ServiceToken) arka plan servislerinin ve worker'ların güvenli makine-makine (M2M) haberleşmesini sağlarken, identity login (OAuth) gerçek kullanıcıların tarayıcı veya masaüstü uygulaması üzerinden kimlik doğrulaması yapması içindir. Google identity login sadece temel kimlik yetkileri (openid email profile) talep eder, Gmail otomasyon yetkilendirmesi (Vault) tamamen ayrı bir onay aşamasıdır.
  • Tarayıcı Tabanlı CSRF Risk Detayları: OAuth akışının güvenliği için CSRF (Cross-Site Request Forgery) koruması elzemdir. Başlatılan oturum talebine ait benzersiz state değeri hem kullanıcının tarayıcısına çerez (browser-bound cookie) olarak yazılır hem de sağlayıcıya gönderilir. Callback adımında bu iki değerin birebir eşleşmesi ve daha önce tüketilmemiş olması zorunludur; aksi takdirde istek reddedilir.

5. Komut Kitabı — doğru kabuk ve güvenli preflight

Önce kabuğu doğrula: PS C:\> Windows PowerShell'dir; $ veya # Linux/SSH shell'dir. Windows dotnet publish, tar ve scp komutlarını SSH ekranına; Linux systemctl, journalctl ve curl 127.0.0.1 komutlarını Windows PowerShell'e yapıştırma.

[SALT-OKUNUR] Canlı Server preflight (Linux / SSH shell)

systemctl status vortex-server --no-pager -l
systemctl show vortex-server --property=ExecStart --property=WorkingDirectory --property=User --property=EnvironmentFiles --no-pager
readlink -f <SERVER_RELEASE_ROOT>/current
dotnet --list-runtimes
nginx -t
curl -fsS http://127.0.0.1:5000/health
curl -fsS http://127.0.0.1:5000/health/worker

Önce loopback health kontrol edilir; sonra operatorın doğruladığı <PUBLIC_SERVER_ORIGIN> üzerinden public health kontrol edilir. Loopback başarısızsa service/config/runtime/data-permission problemi çözülmeden Nginx, DNS veya public proxy değiştirilmez.

[RUNTIME DEĞİŞTİRİR] Normal start/restart

systemctl restart vortex-server
systemctl status vortex-server --no-pager -l
curl -fsS http://127.0.0.1:5000/health

Restart yalnız ilgili servisi etkiler; Nginx, Worker veya başka servisleri rutin Server restart için yeniden başlatma.

6. Private versioned release

[RUNTIME DEĞİŞTİRMEZ] Windows PowerShell'de private publish ve paket doğrulaması

./scripts/windows/publish-server-private.ps1
Get-FileHash <ARCHIVE_PATH> -Algorithm SHA256

Publish çıktısı private altyapı paketi sayılır. Public GitHub, ticket veya chat içine yükleme. Bu script uzaktaki Server'a upload veya restart yapmaz.

[DEĞİŞTİRİR / OPERATOR ONAYI GEREKİR] Sürümlü activation

# Linux/SSH: aktif hedefi kaydet; yeni release önceden checksum ile doğrulanmış olmalı
OLD_RELEASE="$(readlink -f <SERVER_RELEASE_ROOT>/current)"
NEW_RELEASE="<SERVER_RELEASE_ROOT>/releases/<RELEASE_ID>"
test -f "$NEW_RELEASE/Vortex.Server.dll"

# Yeni hedefi atomik değiştir ve yalnız Server'ı yeniden başlat
ln -s "$NEW_RELEASE" <SERVER_RELEASE_ROOT>/current.next
mv -Tf <SERVER_RELEASE_ROOT>/current.next <SERVER_RELEASE_ROOT>/current
systemctl restart vortex-server
curl -fsS http://127.0.0.1:5000/health

Mevcut aktif release silinmez. Protected environment/drop-in dosyaları yerinde kalır; publish payload'ına kopyalanmaz veya görüntülenmez.

Önerilen release düzeni: systemd versioned bir release dizinindeki DLL'i current bağlantısı üzerinden çalıştırır. Kendi operator-managed unit dosyanı incele; bağlantı değişimi ve restart yalnız doğrulanmış release için yapılır.

9. Kalıcı data, SQLite ve yedek sınırı

Release rollback, data restore değildir. current bağlantısını geri almak yalnız kod sürümünü geri alır. Kalıcı data/SQLite geri yükleme ayrı bakım işlemi ve ayrıca onay gerektirir.
  • Vortex__DataDirectory altındaki tüm kalıcı state yedek kapsamındadır: SQLite ana dosyası, varsa WAL/SHM sidecar'ları, kullanıcı dosyaları ve Server tarafındaki private runtime state.
  • WAL modunda çalışan SQLite için aktif servis sırasında yalnız ana DB dosyasını kopyalama; tutarsız olabilir.
  • Servis kapandığında vortex.db-wal ve vortex.db-shm dosyalarının ortadan kalkması normal olabilir. Backup prosedürü sidecar dosyalarını yalnız varsa eklemeli; yokluk nedeniyle release activation yarıda bırakılmamalıdır.
  • Environment/secret manager materyali data archive içine eklenmez. Şifrelenmiş provider verisini geri yüklemek için uyumlu secret material ayrı, operator-controlled mekanizmada korunmalıdır.

[SALT-OKUNUR] Data yolu ve dosya varlığı

systemctl cat vortex-server
find <DURABLE_DATA_DIRECTORY> -maxdepth 2 -type f \( -name 'vortex.db' -o -name 'vortex.db-wal' -o -name 'vortex.db-shm' \) -printf '%p %s bytes\n'

Bu rehber genel-purpose restore komutu vermez; canlı data restore, servis stop, sahiplik/izin doğrulaması ve health testleri içeren ayrı bir onaylı incident prosedürüdür.

10. Atomik aktivasyon ve rollback

  1. Yeni release payload ve checksum doğrula.
  2. Production secret/drop-in ayarlarının yeni release ile uyumunu doğrula; secret kopyalama veya görüntüleme yapma.
  3. Önce loopback health kontrolü yap.
  4. Önceki release bağlantısını sakla, sonra current bağlantısını atomik değiştir.
  5. Yalnız ilgili servisi restart et; loopback ve public health kontrolü yap.
  6. Failure durumunda önceki release bağlantısına dön ve service loglarını secret temizleyerek incele.

[DEĞİŞTİRİR / OPERATOR ONAYI GEREKİR] Copy-ready symlink rollback

KNOWN_GOOD_RELEASE="<SERVER_RELEASE_ROOT>/releases/<OLDER_RELEASE_ID>"
test -f "$KNOWN_GOOD_RELEASE/Vortex.Server.dll"
ln -s "$KNOWN_GOOD_RELEASE" <SERVER_RELEASE_ROOT>/current.rollback
mv -Tf <SERVER_RELEASE_ROOT>/current.rollback <SERVER_RELEASE_ROOT>/current
systemctl restart vortex-server
readlink -f <SERVER_RELEASE_ROOT>/current
curl -fsS http://127.0.0.1:5000/health

İlk rollback sırasında failed veya önceki release dizinlerini silme. Önce loopback, sonra public health doğrula.
